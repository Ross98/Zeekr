## 根因与修复

1. `ArchiveReader._iter_rows` 每页保留月初扫描下界，OR 游标条件继续筛除已经消费的前缀。后段 512 条查询约执行 234.7 万条 SQLite VM 指令；推进扫描下界到当前游标时间后约为 7000 条。完整 20001 条元数据回归从 4175000 条指令降至 401000 条。冻结水位、同时间戳 id 排序、前驱语义和跨月行为保留，没有改索引或业务库。
2. 单独分页修复仍在停车阶段超时。服务器剖析确认逐条 `gzip.GzipFile` 包装及缓冲读取开销显著。改用原生 zlib gzip 解码；输出总量限制为声明长度加一个检测字节，输入块限制为 64 KiB，避免巨大 unused_data 尾部复制。仍检查 gzip 成员 CRC、完整结束、声明长度、SHA-256 和 JSON 字典；保留多成员与零填充支持。
3. Web 每阶段开始和校验完成后原子保存进度，以及 cgroup 内存与 CPU 计数。超时仍能识别已完成阶段和当前阶段。父采集器另有 30 秒终止观测宽限，worker 的 `RuntimeMaxSec=600` 没有增加。
4. 内存采样保留 MemoryHigh、MemoryMax 回收事件、匿名内存、文件缓存和近峰 memory.stat。手动停止旧诊断暴露了 unit 消失后 MemoryMax 变成 `infinity`、结果采集执行 `int()` 失败的问题；最终工具先检查负载完成和有限额度，失效 unit 不能通过，也不会阻断结果保存。

解压回归使用 3 MiB 的压缩正文，却声明长度为 2 字节；原 `tracemalloc` 可见峰值 8451962 字节，新实现 44070 字节。断言上限为 256 KiB；这是 Python 分配观测，不是整个进程或 cgroup 峰值。CRC 损坏、截断、非法尾部、大成员跨输入块、多成员和跨块零填充均有覆盖。

## 内存余量仍待关闭

月报近峰采样含约 38.70 MiB 匿名内存和 83.27 MiB 非活跃文件缓存，dirty、writeback 均为 0。Web 近峰采样含约 25.89 MiB 匿名内存、160.23 MiB 非活跃文件缓存，其中 dirty 约 1.11 MiB。文件缓存占主要部分，因此 cgroup 峰值不能当作 Python RSS 或不可回收堆内存。

`memory.current` 与 `memory.stat` 来自相邻采样读取，不是原子快照，也不能当作精确峰值构成。独立的 anon/file 最大值不能相加后充当一次完整峰值。

月报触及硬限额且发生 17 次回收事件，表明运行依赖缓存回收，不能称为内存余量充足。同应用的另一轮诊断峰值为 123.14 MiB、max 事件为 0，进一步说明不能只选一次较低峰值关闭风险。后续重点是区分缓存回收延迟与不可回收内存增长，并覆盖更复杂合成道路、图片和采样组合；保持 MemoryMax 与 CPU 配额，不能通过增加限额或清理生产缓存掩盖问题。
