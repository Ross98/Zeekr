2026-09-19，用户明确确认正在交流充电。经授权读取后台已采集的当前绑定车辆缓存，没有额外请求车辆或操控充电。两次车辆时间分别为22:05:07、22:07:07（北京时间），读取时分别约旧12秒、4秒；两次充电组合一致，通用电压/电流为正、剩余时间随时间减少。

只记录以下协议组合及证据边界；不提交车辆身份、精确位置、原始快照、服务器信息或凭据。测试使用合成时钟、测量数值及车辆标识。

## 本次启用

共享`vehicle_state.decode()`新增`charging=True, charging_mode=ac`：

| 字段 | 本车活动组合 |
|---|---|
| `chargeLidAcStatus` | 1，交流口盖打开 |
| `chargeLidDcAcStatus` | 2，直流口盖关闭 |
| `chargeSts` | 0，只是组合成员，不能单独解释未充电 |
| `chargerState` | 2，只作为本组合成员 |
| `statusOfChargerConnection` | 3，只作为本组合成员，不单独解释插枪 |
| `chargeUAct / chargeIAct` | 均合法且大于零 |
| `dcChargeSts / dcChargePileIAct` | 均为0 |
| 直流字段 | 不含非法值；合法非零桩侧电压不否定交流活动 |
| 动力/速度 | 无有效行驶或动力就绪冲突 |

布尔、空串、非法字符串、非有限数、缺少必需字段或组合不匹配不能确认活动。活动组合中电流暂时为0只变为未知，不据此停止/重开会话。通用零状态或停止文字不能覆盖非零通用电流/非法电气字段。

解码规则版本升为`we86-v2-ac`。正在跨版本的活动报告标不完整，已存事件与已冻结正文不回填、不重发；新历史对比不混用旧解码版本。

网页和报告都显示“交流”；交流口盖1可显示打开。报告另存`ac_voltage/ac_current`，不替代原直流桩侧`voltage/current`。剩余分钟仍称“车辆估计”，不视为目标SOC。

## 同轮截图补证：交流观测功率

用户随后提供当晚22:12的官方App及充电桩App截图：两者各自的同屏电压×电流均与其显示功率按显示精度吻合，API通用电气值与该交流场景相符。因此本车已核验活动组合下，启用`chargeUAct × chargeIAct / 1000`，明确称“交流观测功率（电压×电流）”，不称独立功率传感器或桩计费电量。两App数值不同，不把它们拼成同一条观测，也不据此计算充电损耗。

最高/平均功率沿用已有采样与覆盖门槛；仅同次、同模式、合法正U/I参与，未知和停止点不跨越、不补零。此规则只对应本车当前已核验组合，不推广其他交流接法或车型。截图原图、站点名称、枪号、车牌、账单均不入Git。

截图能证明该时刻的目标电量和已充时长，但接口中未找到独立可靠字段；不能将截图目标写成全局常量，也不能自动倒推/补造本程序未采集的起点与过程。
