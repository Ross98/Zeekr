# 状态查询频率：配置与短窗口实测

## 60 秒的来源

`query_policy.py` 的 `INTERVAL = 60` 最早出现在 2026-09-17 的初始提交 `93bf66c`。它控制本地成功查询缓存、账号状态查询间隔，以及缺少可用 `Retry-After` 时的默认等待时间。后台正常采集也使用 60 秒。

这些是本项目配置，不能据此宣称极氪服务端限制为每分钟一次。已检索的公开文档与仓库资料没有给出当前状态端点、当前账号已核验的持续请求配额。

## 经用户授权的有界测试

- 时间：2026-09-20 20:34:17 至约 20:38:10，北京时间；测试循环 233.27 秒。
- 当前已登录账号、当前绑定车辆，使用现有客户端的状态 GET；不登录、不发控制指令、不修改车辆数据、不发送通知。
- 独立诊断进程临时跳过本地状态缓存和账号 60 秒间隔。保留同一跨进程请求锁与网关冷却；首次 HTTP 429、认证失败、网络异常或绑定变化即停。
- 上限：40 次测试请求、8 分钟；实际 30 次状态请求。车辆列表另通过正常缓存/保护查询一次。常规后台保持运行，因此这不是排除所有其他客户端流量后的独占压测。
- 在执行前，4 项离线测试验证共享冷却、429 持久化、单次限流即停、请求数/时长上限、本地缓存隔离与非状态操作拒绝。

## 能说明什么

- 当前账号/端点在本轮短窗口内接受了每秒一次的状态查询；本轮没有找到真正的限流边界。
- 最短档仅 8 次请求，不能外推为持续每秒一次、全天调用量、其他接口或其他账号的安全配额；请求全部成功不能证明无限制。
- 30 次返回只有一个源状态时间和一个位置；没有新坐标。测试开始时该状态已陈旧约 712 秒，结束时约 945 秒。因此本轮只验证了接口可请求得更快，未验证车辆行驶时定位上报能否更密。
- 若需评估轨迹改善，应在正常行驶、有新车端上报的窗口内比较新坐标增量、状态年龄和限流情况；不能把重复旧缓存当作更多轨迹点。
