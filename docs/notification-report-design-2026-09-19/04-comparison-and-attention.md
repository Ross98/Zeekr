# 04 · 历史对比与状态提示

目标：让参数有上下文。只解释观测差异，不打驾驶分、不诊断车辆。此文件所有样本数、相似度和展示阈值均为设计默认，需版本化。

## 1. 显示策略

- 对比只进已有trip_end/charge_end消息。开始充电没有完整区间，不做“本次比上次快”的预测。
- 每条最多两项历史对比；优先用户能理解的单位，保留样本数及口径。
- 数据不足/不兼容则不显示比较块；私有报告保留原因，不在每条消息反复说“历史不足”。
- 正常状态留正文；可靠且需要留意的状态置顶；未知列为“未确认”，不冒充异常。
- 同一次报告的比较和提示在事件结算时冻结。以后补采、换配置、增加历史，不改变已排队正文或已发送事件。

## 2. 本车历史对比

### 2.1 共用筛选

1. 仅同一车辆摘要、同kind、v2且公式口径兼容的完成事件。无须通知已送达；业务事件与delivery状态独立。
2. 历史事件end_time必须早于本次start_time，且在本次start_time之前90天内；排除重叠、未来时间、当前事件、重复ID。
3. partial必须严格为false；相关指标有效、无升级中途接入、无充电污染或关键断档。缺质量字段不默认为合格。
4. 配置/口径：能耗比较要求容量及其来源/口径一致；达成率还要求额定续航与标准一致；功率要求电气侧、单位、模式、公式一致。decoder版本通过明确兼容表，否则排除。
5. 按end_time降序、event_id作稳定次序，从最近至多500条索引记录中筛选；每项最终取最近20条合格样本，至少5条才比较。上限截断记录在私有selection metadata。
6. 每项用中位数，不混用平均数。“比历史中位数…”；当前值不放入基准。基准为0则百分比不可用，可保留单位差值。
7. 读取失败/索引无数据，只抑制比较；不补请求车辆，不阻断通知。跨车、跨版本和索引损坏的情况有专门测试。

90天/500条/20条/5条是首版性能和可读性的折中。必要时配置化，但不得悄悄放宽到所有车型或不完整事件凑样本。

### 2.2 行程比较

相近距离：历史D在本次D的80%–120%内；两边D均≥10km。不能仅凭距离称“同一路线”“通勤”或“同路况”，首版不使用私有地址/坐标聚类。

| 比较项 | 附加条件 | 结果表达 |
|---|---|---|
| 每公里用时 | D、T有效，完整记录 | 本次 T/60/D 分钟/公里，与相近里程样本中位数比较；不能把总耗时差完全当拥堵差 |
| 估算百公里耗电 | 满足03能耗门槛；历史平均速度在本次±25%内；两者有效起止车外温度均有且端点均值差≤5°C | 本次X，对照中位数Y，差值X−Y；只说观测差异 |
| 额定续航达成率 | 同标准/额定配置，满足03门槛和上述环境条件 | 百分点差；优先级低于耗电，默认二者只出耗电以免重复 |

平均速度为0时不构建百分比速度范围；不进行能耗匹配。温度只是有限背景筛选，不能证明风、坡度、载重、空调或交通相同。温度缺失时仍可比较每公里用时，但能耗比较不降格为“同条件”。

样例（假数据）：

```text
【本车历史参考】
相近里程8次：本次每公里1.8分钟，历史中位数2.0分钟。
里程、平均速度及车外温度接近的6次：
本次估算21.9，历史中位数23.4 kWh/100km。
路况、风温及载重未完整匹配，仅供观察。
```

不同指标可有不同n；不能把8个里程样本数量套在只有6个能耗样本上。百分比可省，单位差更直观。反向改善/恶化不用“驾驶更好/更差”评价。

### 2.3 充电比较

同确认模式，历史起始SOC在本次±3个百分点内、结束SOC在±3个百分点内；本次和候选SOC增加均≥10个百分点。对比范围称“相近电量区间”，不声称严格同一30%–80%。

| 比较项 | 附加条件 | 呈现 |
|---|---|---|
| 每增加1个百分点的观测用时 | 完整且SOC、时长有效，03定义的charging_time_coverage≥80%，开始非中途；末活动/停止观测之间车辆时间及本机时间间隔均≤180秒 | T/60/SOC增加，单位分钟/百分点；停充实际时刻仍可能介于观测之间 |
| 观测区间平均功率 | 03均值门槛通过，模式/电气侧一致，各自功率覆盖≥80% | 本次/历史中位数kW，并保留“观测”限定 |
| 最高采样功率 | 仅辅助，不作为默认主比较 | 采样易错过峰值，不据此判断桩是否达标 |

首版不插值构造精确SOC子区间，不把不同起终SOC的总分钟直接作充电速度结论。未来有电池温度、目标和可靠连接规则后，可增加分组，但不能回填当前缺失字段。

充电地点未作等价判断，电池温度、桩额定能力目前不全。文案须写“不同桩与电池温度可能影响结果”，不写“本站变慢”“电池老化”或“充电故障”。

### 2.4 可复算与查询成本

私有comparison保存：规则版本、时间截止点、输入指标、候选数、采用event IDs、每项n、基准中位数、当前值、差值和排除原因计数。候选ID最多20/项，不保存全部500条报告正文。

以03的report_metric_index查询，避免每次发送全表扫描大JSON。历史读取在结算阶段运行，限定最多500行；无法完成时置unavailable继续基础事件。发送阶段不再查询历史。测试从同一输入、同一索引快照得出完全相同结果。

## 3. 状态提示与排序

### 3.1 分级

| 等级 | 意义 | 举例与边界 |
|---|---|---|
| 车辆明确警示 | 已核验的原车告警、时间有效 | 将来可信胎压报警；目前没有该能力，默认不产生 |
| 需要留意 | 在此事件语境下，明确、持续的状态值得用户检查 | trip_end停车后已确认未锁/车门未关/车窗未关；编码未核验时不可启用 |
| 状态说明 | 普通状态，不一定需要动作 | 直流口盖打开、充电已停止、未来确认枪仍连接 |
| 未确认/记录说明 | 数据不足或陈旧 | 右后窗未确认、停车状态未更新、功率缺样 |

排序：车辆明确警示→需要留意→核心事件结果→其他状态。只在已有消息里体现，不建独立告警/恢复事件。未知不能升级为未关/低压/危险，也不能被省略成“全车正常”。

### 3.2 提示条件

统一要求：字段能力enabled、值有效、对应状态时间在事件结算参考点180秒内、无动力/移动冲突；独立字段时间存在时也要有效。只有整车时间的字段，提示措辞明确“云端观测”。

| 候选提示 | 启用后的条件 | 当前落地 |
|---|---|---|
| 停车后未锁 | trip_end，停车后连续两条独立、≤180秒间隔观测明确未锁，最新仍新鲜 | 未锁编码缺证据：只显示锁车未确认 |
| 停车后车门/窗/尾门未关 | trip_end，对应开状态规则已核验；同上两条连续观测仍开 | 非0未核验：只显示对应项未确认 |
| 停止后仍插枪 | charge_end，connector_state=connected且新鲜 | 未来仅状态说明；不是故障，不提醒必须拔枪 |
| 直流口盖打开 | 正文列真实状态；只有另有可靠未连接条件且产品明确需要时才考虑注意提示 | 当前正常状态说明，不能因充电站口盖打开发异常 |
| 车辆胎压报警 | 原车已核验报警激活且对应时间有效 | 当前缺报警字段映射，禁用 |
| 充电中断 | 明确原因字段已核验为异常中断，且事件对应 | 当前停止原因未知，不据低于目标或0A认定 |
| 目标未达 | 可靠目标且结束SOC小于目标 | 仅事实“停止时电量低于设定目标”；不自动升为故障 |

只观察到一条可靠打开/未锁状态时，正文写“观测到…”，不置顶为持续提醒；缺少第二条不通过重复缓存凑数。门窗开的具体位置始终保留，不笼统写“门窗异常”。

充电开始时人在车内/上下车是正常场景，不把门开或未锁直接套成停车遗忘提醒。车辆明确警示若将来可用，可在任一既有报告展示，仍不创建新的推送类型。

### 3.3 变化与恢复

- 两条真实有效时间点不同才记录变化；重复缓存没有新变化。
- 未知→关闭/已锁：叫“后续确认关闭/已锁”；不叫“已恢复”。
- 明确打开/未锁→关闭/已锁：可写“后续观测已关闭/已锁”；不声称准确动作时间。
- 旧的注意状态随后明确恢复，在最终报告中不置顶；有价值时留一行变化记录。
- 最新变未知或陈旧：写当前未确认，原注意状态只能带原时间作为历史说明；不能继续当当前警示。
- 一事件同项去重；按对象/维度保留一条当前结论。最多三条置顶，其余按01预算保留数量和私有详情。

## 4. 为什么不默认加更多“诊断”

现有数字胎压、胎温、功率变化足够做报告，不足以判定故障。自设胎压报警需另有本车推荐值、冷/热胎语境、容差、持续时间、传感器异常区分；当前设计不借缺少原车报警位自动引入这套新规则。

同理，续航下降多于实际里程不等于电池衰减；后段充电功率下降不等于过热；插枪未充电不等于故障。设计完整包含这些状态的呈现和未来证据入口，不包含未经验证的诊断结论。
