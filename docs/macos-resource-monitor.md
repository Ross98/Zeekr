# Mac mini 资源巡检与 Bark

独立用户任务 `local.zeekr.resources` 每约 60 秒读一次本机指标，运行入口 `python3 -m zeekr_control.resource_monitor`。它与 Web、车辆采集、报表任务分开，复用服务 HOME 与既有私有 `bark.json`。不读取车辆接口，不控制车辆，不自动停止进程或删除数据。任务以 Nice 10 运行；它提供持续超限软预算告警，不是 Linux cgroup 硬限额。

## 采样与判定

| 指标 | 提醒 | 严重 |
|---|---:|---:|
| 主机 CPU（全机合计 0–100%） | 85% | 95% |
| Zeekr 三任务及所有后代进程 CPU（100%=一核） | 100%，进程预算提醒 | 不以进程预算判定系统严重压力 |
| Zeekr 进程树 RSS 合计 | 512 MiB，进程预算提醒 | 不以 RSS 判定系统严重压力 |
| macOS 内存压力 | warning | critical |
| 三个既有服务任务 | — | 连续无法取得运行任务 |
| 本机网页、配置的 HTTPS 入口 | — | 访问或匿名认证边界异常 |
| 指标不可读、CPU 窗口持续不完整、巡检心跳过期 | 监测失效，不能据此判断压力或恢复 | 不冒充资源耗尽 |

主机 CPU 来自 Darwin `host_statistics(HOST_CPU_LOAD_INFO)` 的累计 user/system/idle/nice tick 差，覆盖整个实际巡检间隔，通知写出窗口秒数；首个窗口预热，超过 180 秒重建窗口。不再把每分钟一次的一秒 `top` 快照说成持续平均值。

进程 CPU 来自 `ps -S` 累计 CPU 时间差，包括已退出并由父进程回收的子进程。比较整棵树的累计值，避免子进程退出后既漏算又重复算。正常的新生子进程、已退出子进程不再让整个窗口作废；根任务重启、PID 重用、活着的子进程脱离树、计数倒退或长时间中断则保留“不完整”，不拿部分和证明恢复。RSS 是进程 RSS 相加，可能包含共享页重复统计，不当作 Python 堆或全机物理内存占用。

进程预算是诊断提醒，不是内存配额或 CPU 硬限制。例如 10 核主机上的 200% 进程 CPU 约占全机 20%；RSS 超过 1 GiB 不表示 16 GiB 主机内存不足。Bark 区分“进程预算提醒”“系统资源压力”“服务可用性异常”“资源监测失效”，仍使用既有 active 推送级别。

内存使用 [Apple XNU 导出的 dispatch 压力值](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c)：sysctl `kern.memorystatus_vm_pressure_level` 的 1/2/4 分别映射正常/提醒/严重，不混用内核内部枚举。剩余内存少不单独触发告警，避免把缓存误判为压力。

每个原因分别连续 3 个有效巡检点确认异常、等级变化与恢复，通常约 2–3 分钟；CPU 高、RSS 高、内存压力高各出现一次不能凑成三次。调用过快、休眠或长时间中断不能虚增连续次数。主机 CPU 严重线恢复须低于 90%，提醒线恢复须低于 76.5%；CPU／RSS 预算恢复须低于原提醒线的 90%。

初始正常、首个 CPU 窗口预热保持安静；连续三次读数失败或窗口不完整报监测失效，不编造 0。一个指标未知，保留该项此前已确认的异常；其他指标仍能独立恢复。消息同时说明已恢复项与尚未证实恢复项。

网页探测不携带凭据：本机和 HTTPS 各检查根路径 200、匿名 `/api/state` 401。每个请求限时 2 秒，不跟随重定向、不走环境代理、不绕过正常 DNS 或证书验证。HTTPS 来自实际用户的 Web LaunchAgent `ZEEKR_PUBLIC_ORIGIN`，不硬编码主机名。

## 持久状态与投递

`resource-health.json` 保存在私有应用数据目录（目录 700、文件 600），记录最近样本、采样进程 PID、每个原因的连续计数与确认等级、事件签名、投递状态及重试时间。独占 `resource-monitor.lock` 防止重复实例。旧状态迁移保留已确认异常与发送结果，不能归因的旧总计数重新确认，避免升级时凭空补发。

- 确认异常或恢复时发 Bark；新原因即使同级也独立确认后提醒。相同原因组合且上次已确认成功，最多每天提醒一次。
- 发送前必须先持久化 sending 意图；状态写失败不发消息。
- 明确失败按 15 分钟重试，永久错误按 1 小时重试；发送前重新核对当前原因，不用新异常重发旧原因。停止或执行时限到达不开始新网络发送。
- 不确定结果或重启时留下的 sending 变为 uncertain，不自动重发。同级日提醒也不重发 uncertain；后续新等级变化另行记录。
- 状态变化保存的发送结果只表示 Bark 服务端响应；不证明手机实际展示。测试使用合成样本与替身发送器，不发真实测试消息。

## 检查与发布

以实际服务 HOME 运行；若从普通开发终端查看线上状态，显式指定 `--root` 为 `ZeekrServer/state/Library/Application Support/ZeekrControl`。

```sh
python3 -m zeekr_control.resource_monitor --root '<实际应用数据目录>' --inspect
python3 -m zeekr_control.resource_monitor --sample
```

`--inspect` 只读已保存状态，`--sample` 只读本机指标；均不写状态、不发通知。资源任务日志在运行根目录 `logs/resources.stdout.log` 与 `logs/resources.stderr.log`。

固定发布工具的 `macos stage --resource-monitor` 会先在候选检查模块，然后在切换时安装资源 LaunchAgent。既有三个任务的配置全部备份，资源任务列入后续发布的配置指纹、停服、进程目录及心跳检查。首次安装失败回滚会移除新增资源任务；旧版已有资源任务时恢复其原配置。业务数据始终保留最新状态。只生成候选不安装任务，不跳过最终候选服务用户全量测试。

资源任务同样需要用户登录后才启动；机器关机、休眠、掉网或无法写盘时，本机 Bark 不是独立外部可用性监控。存储巡检仍由既有投递后台每 5 分钟执行，现有磁盘告警门槛和事件去重保持不变。

现有投递后台另外检查资源巡检心跳：超过 180 秒、时间在未来或状态不可读，连续三次检查确认后报监测失效。使用独立 `resource-watchdog.json`，不与巡检进程竞争写同一状态；车辆采样暂停、磁盘巡检报错时仍检查。只在实际资源 LaunchAgent 对应的数据目录启用，不给其他部署或测试目录凭空增加告警。这能覆盖资源任务单独停摆；整机掉线或两个观察者同时停摆仍须外部监控。

## 磁盘口径与历史调查

早期调查把文件系统即时空闲误当 macOS 全部可用空间，导致用户仍有大量预计可回收空间时收到严重告警。现已改用 macOS Important Usage 估算可用空间，页面和通知另列即时空闲；读取失败报未知，不能退回旧口径断言严重。详见 [存储管理](server-storage-management.md)。当前门槛仍为估算口径使用率 80%／90%，或可用 5／2 GiB；inode 独立 80%／90%，并保留原恢复回差。

历史目录分配量仅用于解释当时即时空闲较少，不是当前容量结论，也不能相加作为精确归因。未删除缓存、开发工具、iCloud 文件或备份，未操作下载状态。此次 CPU／内存规则修订不改变已经修复的磁盘口径。
