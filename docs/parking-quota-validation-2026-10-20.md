## 固定候选、环境与预算

候选 Git 为 `d1fb05748f9bb4d77f66583d47a95a2cfaa615c6`，导出只读源码副本。应用源码与生产 `3f6e4af` 相同；每轮绑定源码、工具和镜像哈希。所有查询在本机 Docker Linux VM 的合成卷内串行运行。生产只读获取配额，不在生产主机运行负载、读写业务库或修改限额。

实测生产 Web cgroup：CPU `25000 100000`（25% 单核），`memory.high=201326592`（192 MiB），`memory.max=268435456`（256 MiB），`memory.swap.max=0`，`pids.max=64`，文件大小上限 512 MiB。Docker 预检已核对同值，软限由 VM 内控制器只写入本次合成容器的 cgroup。查询容器无网络、只读根目录、只读候选与数据、UID 1000，丢弃能力；只允许写独立合成工作卷。资源统计包含监督进程及查询子进程。

用户选择本机 Docker，并要求结合服务器资源推荐预算。据此在正式测量前按 Web 已分配的资源固定下表。补充只读盘点（2026-10-20 10:49 北京时间）：主机 4 vCPU、约 3.64 GiB RAM；Web 的 25% 单核约占主机总 CPU 的 6.25%。整月 300 秒目标最多约 75 CPU 秒，串行查询保持这一开销上界。主机盘点为时点背景，验收始终使用预先固定的 Web cgroup 配额与预算。



| 项目 | 验收目标 | 理由 |
|---|---|---|
| 单日 | ≤60 秒墙钟 | 在 25% 单核下约 15 CPU 秒；历史扩读仍需交互可等待 |
| 整月 | ≤300 秒墙钟 | 约 75 CPU 秒；旧同配额整月停车 262.175 秒仅作选取目标的参考，不是新结果 |
| 单次硬停止 | 600 秒 | 保留失败证据，超过目标可继续测完整结果，最多等到此上限（约 150 CPU 秒）；旧组合 600 秒不冒充停车 SLA |
| 峰值内存 | ≤192 MiB | 不越过生产软回收线，保留距硬限 64 MiB（25%）的空间 |
| 硬限、OOM | memory.events 的 max/oom/oom_kill 增量均为 0 | 没 OOM 不等于有稳定余量 |
| 取消 | 信号后 ≤2 秒完成清理并释放两个 worker 名额 | 分开记录同步应答与后台排空，不能只看按钮应答 |

生产为 Linux x86_64，本机 Docker 为 Linux aarch64；相同配额不代表相同 CPU 吞吐、内核或磁盘。报告仅证明这个隔离等配额环境的结果，不替代生产架构的耗时 SLA。镜像固定为拉取后的 SHA-256。实测运行时为 Python 3.12.15、Linux 6.12.76-linuxkit aarch64、glibc 2.36；Docker Engine 29.6.2，cgroup v2。Docker VM 为 8 vCPU、约 3.83 GiB RAM，查询仍受单独的 25% 单核与 256 MiB 硬限约束。

## 场景与结果合同

16 格矩阵：单日（2026-08-16）/整月（2026-08-01—31）×短历史（31 天）/长历史（90 天）×邻接完整/缺前/缺后/无行程。每格冷、暖各三次；每轮另测一次取消。完整 31 天有 267,840 条采集，90 天有 777,600 条，均为 10 秒密度。

所有位置保持不变。8 月 16 日中午一小时连续返回旧缓存，保留所有采集行但形成有效车辆观测缺口。每天一条恒定 SOC 的合成充电摘要用于测历史事件读取与阶段边界成本，不是实车充电模型。前后行程只作为边界证据，不用新增历史行程偷偷补齐“缺前/缺后”。

每次检查完整响应哈希、v6 版本、唯一位置连续事件、预先计算的完整起止时间/时长、开放端标记、有效观测缺口、未知 SOC 耗电和未知 kWh。无行程的单日查询仍须返回整个 31/90 天长停车，不允许裁短换速度。冷暖及三轮完整响应必须一致；无完整响应、超时、容量错误、OOM 均逐次保存并判失败，不作为正确性通过。

冷：新进程，只对这份合成 SQLite 使用 fsync + POSIX_FADV_DONTNEED；不清 Docker VM 全局或生产缓存。暖：同一进程在完成冷查询后再查询。若冷查询失败，后续只能标“部分暖缓存”，不能计入有效暖样本。暖查询前通过保持打开的 memory.peak 文件描述符重置其峰值；不支持重置时明确保存保守的生命周期峰值。所有进程、容器及数据都仅属本次测试。

记录逻辑扫描行（归档迭代实际返回的元数据、事件解码行）、正文解压次数、读取区间、阶段耗时、墙钟、CPU 秒、cgroup 精确/采样峰值、high/max/OOM 事件、完整响应、取消排空及临时文件。扫描行不是数据库物理页 I/O；冷缓存也不宣称物理磁盘完全冷。

测量工具为 `tests/parking_quota_workload.py` 与 `scripts/parking_quota_matrix.py`；小样本合同测试先失败再实现，涵盖完整响应对照、长事件不裁短、缓存缺口与真实 AnalysisJobs 最后订阅取消。验收器另检验“无 OOM 但触及硬限”、部分暖缓存、取消只应答未排空等不能误判为通过。

## 小试（正式矩阵的第 1 轮）

小试与后续矩阵使用相同候选、工具哈希、镜像和合成卷，保留为对应场景的第 1 轮，不另挑样本。

`memory.high` 是回收阈值，允许短时超过；超过预设目标与触及硬限、OOM 分开报告。这里采用 cgroup 总内存，包括文件缓存与监督进程，不把它写成 Python RSS。小试不能证明三轮稳定性，也不能代表其余 14 格场景。

## 最小优化候选

只调整停车查询的临时投影。公共归档元数据把键名与已经存为标量列的时间/变更字段去重，读取时重建完整记录；未知扩展字段保留原 JSON。位置投影保留停车判断、坐标系和可信度实际使用的五个字段，公共结果命名前后的行为保持一致。直接 `build_events` 使用原完整投影。

不改归档读取上下界、正文选择、停车事件算法、工作文件上限或生产配额；没有持久缓存和历史数据迁移。固定 1 MiB 临时预算的回归在旧实现失败，优化后能返回完整 90 天事件，整个公开响应与原存储实现相同。2,160 行小样本逻辑页数从 396 降到 127（约减少 68%）；这是空间收益，不冒充等配额耗时或整月验收。

首个优化候选的短历史无行程小试：冷查询 140.525 秒，暖查询 195.367 秒，完整响应 SHA-256 与基线相同；两次峰值均为 192.25 MiB。冷查询有改善，暖查询没有稳定收益，单日时间与内存目标仍失败。不能据此声称性能优化已经达标。

长历史无行程查询已完成 777,600 行元数据、777,240 次正文解码，临时工作文件约 178.6 MiB，投影阶段 434.998 秒；仍未获得完整查询响应。避免把“越过原容量错误”当作完整正确性或时间验收通过。

### 按用户要求减少重复工作

用户要求“减少重复无意义劳作”后，已停止首个优化候选的长历史失败后恢复暖测，保存主动停止记录和阶段进度。未完成的查询不计入有效样本，不继续重复同一已知失败。

后续采用以下执行规则：

- 调试阶段先做一次有界性能采样，定位主要调用成本；不继续运行完整冷暖矩阵。
- 每项优化只做一个能检验假设的前后对照。没有明确收益就停止该方向，避免靠重复测量寻找较好结果。
- 输入、源码、工具、配额均未变的有效证据复用；跨候选不复用性能样本。最终候选固定后，再一次性执行必要验收。
- 已知容量失败、硬超时、OOM 的场景先保留首份诊断证据，不继续恢复暖测或机械重复三轮；标为失败/未完成，修复后才重新测。
- 聚焦测试随改动运行；完整后端回归只在最终候选形成或相关输入改变后运行，不因状态询问或提交动作重复执行。

原定最终通过验收仍要求各场景有效冷暖样本及稳定性；减少调试阶段的重复，不降低停车边界、缺口、未知耗电或完整响应合同。最终候选及逐场景结论待定。
