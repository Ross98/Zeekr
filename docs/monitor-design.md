# 自动行程与充电通知

用户已批准：检测行驶后记录轨迹，下电十分钟后发送里程、耗时、电量变化；充电开始和停止时发送总结。渠道为已验证的企业微信群机器人。实现不提交账号或 Webhook，不自动提交 Git。

## 实现顺序

1. 用合成数据测试新鲜度、行程和充电状态转换、重启恢复、通知重试。
2. 新增保守字段解析、SQLite 状态和通知队列，复用轨迹数据库。
3. 新增独立后台监控命令，与 Web/CLI 共用现有查询锁、缓存和限流。
4. Web 展示监控状态；提供 systemd 服务模板及启停、验证和回滚说明。
5. 运行完整离线测试；部署时核验服务器身份和目录，实车验收与离线验收分别报告。

## 状态与证据

默认每六十秒查询一个绑定的车辆摘要 ID；首次单车自动绑定，多车必须明确选择。新的车辆时间戳才推动状态；超过三分钟、未来超过三十秒、倒退或重复的缓存不推动转换。网络失败只更新运行健康状态。

行驶由有效非零车速或连续新鲜观测的里程增长确认。下电要求 engineStatus=engine_off 且 ptReady=0，矛盾的移动证据优先。停车等待在车辆时间及本机观测时间上都满足十分钟，并有新的下电观测，才结算。中途上电/行驶取消等待；未知动力状态中断确认链。采集缺口标注数据不完整，绝不以断网视为结束。

起点尽可能采用最近三分钟内的上一条非行驶观测；无法获取完整起点时注明。终点冻结于首次确认下电观测，避免停车后充电污染行程电量。起止总里程差为距离；电量百分比不能直接换算 kWh。暂不输出未经验证的累计耗电字段、充满原因或驾驶评分。

充电开始依据正充电电流与有效充电电压，或用户实车核验后的 chargeSts 配置。默认只确认本车已核对的三项全零为未充电，以及明确文字状态；不套用社区猜测数字枚举。插枪、电流为零、旧缓存都不能单独判定充电。首次启动已在充电时标为开始时间未知；停止时只汇总已观测部分。所有未核验枚举保留诊断值，供下次实车校准。

状态、事件和通知待发记录事务写入；轨迹写入可重复执行且以缓存键去重。成功消息不重发。网络超时或进程在发送中终止可能导致对端已收但本地未知，标记待人工确认，不自动重发此类消息；明确失败允许指数退避，最多六次。消息含稳定事件编号。Webhook 接口不提供端到端 exactly-once 保证。

## 部署与限制

独立 monitor 服务不依赖浏览器，SQLite 保持本机私有权限。Webhook 存在仓库外、权限 600 的配置文件；只向固定 HTTPS 企业微信域名发送，不跟随重定向。整个监控进程持有独占锁，防止本机双进程重复通知。部署只启用服务器一个实例。

本地已验证群机器人收信，服务器 SSH 当前需要交互扫码。当前云端缓存更新频率、行驶/充电实车状态仍需验证；三分钟新鲜度和连续下电确认会使睡眠车辆的通知延后，优先避免误报。没有完整 GPS 数据时只记录采样点，不补造道路轨迹。
