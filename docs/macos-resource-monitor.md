# Mac mini 资源巡检与 Bark

独立用户任务 `local.zeekr.resources` 每约 60 秒读一次本机指标，运行入口 `python3 -m zeekr_control.resource_monitor`。它与 Web、车辆采集、报表任务分开，复用服务 HOME 与既有私有 `bark.json`。不读取车辆接口，不控制车辆，不自动停止进程或删除数据。任务以 Nice 10 运行；它只为极氪服务可用性告警，整机资源与进程预算只展示，不是 Linux cgroup 硬限额。

## 监控边界

只为极氪服务与数据安全主动告警，不作为整机资源报警器。

| 项目 | 页面／诊断 | Bark |
|---|---|---|
| 主机 CPU、物理内存、macOS 内存压力 | 只读最近保存值，注明时间和过期 | 不发送，严重值、读取失败、恢复均不发送 |
| Zeekr CPU／RSS、CPU 窗口完整性 | 诊断参考，超预算不等于服务故障 | 不单独发送；服务受影响由下列服务检查告警 |
| Zeekr Web／采集／报表任务 | 任务是否运行 | 连续异常确认后发送 |
| 本机网页、配置的 HTTPS 入口 | 根页面与匿名认证边界 | 连续异常确认后发送 |
| 车辆采集心跳 | 遵守采样开关及计划冷却时间 | 已启用且心跳停摆／无法确认时发送；主动暂停不报警 |
| 极氪巡检任务心跳 | 独立看门狗 | 连续过期或不可读后发送 |
| 数据所在磁盘容量、inode | 沿用存储管理口径 | 保留原存储异常／恢复通知 |

设置 → 存储管理中的「极氪服务与资源参考」展示上述资源读数。读取 `/api/storage` 只投影巡检缓存，不执行进程枚举、车辆请求或网络探测；不会写状态或发送通知。接口需网页认证，仅返回白名单标量，不返回进程命令、PID、私有路径或凭据。过期／未来时间标记为无法确认当前服务状态，真实零值保留。

主机 CPU 来自 Darwin `host_statistics(HOST_CPU_LOAD_INFO)` 的累计 user/system/idle/nice tick 差，覆盖整个实际巡检间隔；首个窗口预热，超过 180 秒重建窗口。不再把每分钟一次的一秒 `top` 快照说成持续平均值。

进程 CPU 来自 `proc_pid_rusage(RUSAGE_INFO_V1)` 的自身与已回收子进程累计时间，使用 `mach_timebase_info` 换算为秒；`ps` 只提供进程树、UID、RSS 与运行时长。原生回归发现本机 `ps -S` 未把已回收子进程耗时计入 TIME，不能依赖该选项。比较整棵树的累计值，避免漏算或重复算；原生进程开始时间用于 PID 身份核对。读计数前后两次核对成员集合，采样期间退出或新生会标记不完整，防止回收时重复计数。根任务重启、PID 重用、活子进程脱离树、计数倒退或长间隔同样保留“不完整”，不拿部分和证明恢复。RSS 是进程 RSS 相加，可能包含共享页重复统计，不当作 Python 堆或全机物理内存占用。

进程预算仅为诊断参考，不是内存配额或 CPU 硬限制。例如 10 核主机上的 200% 进程 CPU 约占全机 20%；RSS 超过 1 GiB 不表示 16 GiB 主机内存不足。主机 CPU、内存压力和进程预算不参与服务告警总等级、事件签名、重试、日提醒或恢复通知；对应传感器不可读也不触发 Bark。

内存使用 [Apple XNU 导出的 dispatch 压力值](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c)：sysctl `kern.memorystatus_vm_pressure_level` 的 1/2/4 分别映射正常/升高/严重，只作页面参考。

每个服务异常分别连续 3 个有效巡检点确认和恢复，通常约 2–3 分钟。调用过快、休眠或长时间中断不能虚增连续次数。采集心跳使用已有后台新鲜度规则，遵守 `next_check` 冷却期限；主动暂停采集保持安静。无法读取采集状态只报告无法确认，不编造正常或恢复。初始正常、首个 CPU 窗口预热保持安静。

升级时按 `zeekr-service-v1` 通知范围重新核对旧状态：整机压力、CPU／RSS 预算及其指标异常静默退出告警签名，取消对应待发、失败重试和每日提醒；不补发「已恢复」，不把规则收窄说成资源恢复。已有服务异常及其发送结果保留，新服务异常仍须独立确认。

网页探测不携带凭据：本机和 HTTPS 各检查根路径 200、匿名 `/api/state` 401。每个请求限时 2 秒，不跟随重定向、不走环境代理、不绕过正常 DNS 或证书验证。HTTPS 来自实际用户的 Web LaunchAgent `ZEEKR_PUBLIC_ORIGIN`，不硬编码主机名。

## 持久状态与投递

`resource-health.json` 保存在私有应用数据目录（目录 700、文件 600），记录最近样本、采样进程 PID、每个原因的连续计数与确认等级、事件签名、投递状态及重试时间。独占 `resource-monitor.lock` 防止重复实例。旧状态迁移仅保留范围内的服务异常与发送结果，避免升级时凭空补发。

- 确认极氪服务异常或恢复时发 Bark；新原因即使同级也独立确认后提醒。相同原因组合且上次已确认成功，最多每天提醒一次。
- 发送前必须先持久化 sending 意图；状态写失败不发消息。
- 明确失败按 15 分钟重试，永久错误按 1 小时重试；发送前重新核对当前原因，不用新异常重发旧原因。停止或执行时限到达不开始新网络发送。
- 不确定结果或重启时留下的 sending 变为 uncertain，不自动重发。同级日提醒也不重发 uncertain；后续新等级变化另行记录。
- 状态变化保存的发送结果只表示 Bark 服务端响应；不证明手机实际展示。测试使用合成样本与替身发送器，不发真实测试消息。

## 检查与发布

以实际服务 HOME 运行；若从普通开发终端查看线上状态，显式指定 `--root` 为 `ZeekrServer/state/Library/Application Support/ZeekrControl`。

```sh
python3 -m zeekr_control.resource_monitor --root '<实际应用数据目录>' --inspect
python3 -m zeekr_control.resource_monitor --sample
```

`--inspect` 只读已保存状态，`--sample` 只读本机指标；均不写状态、不发通知。资源任务日志在运行根目录 `logs/resources.stdout.log` 与 `logs/resources.stderr.log`。

固定发布工具的 `macos stage --resource-monitor` 会先在候选检查模块，然后在切换时安装资源 LaunchAgent。既有三个任务的配置全部备份，资源任务列入后续发布的配置指纹、停服、进程目录及心跳检查。首次安装失败回滚会移除新增资源任务；旧版已有资源任务时恢复其原配置。业务数据始终保留最新状态。只生成候选不安装任务，不跳过最终候选服务用户全量测试。

资源任务同样需要用户登录后才启动；机器关机、休眠、掉网或无法写盘时，本机 Bark 不是独立外部可用性监控。存储巡检仍由既有投递后台每 5 分钟执行，现有磁盘告警门槛和事件去重保持不变。

现有投递后台另外检查资源巡检心跳：超过 180 秒、时间在未来或状态不可读，连续三次检查确认后报监测失效。使用独立 `resource-watchdog.json`，不与巡检进程竞争写同一状态；车辆采样暂停、磁盘巡检报错时仍检查。只在实际资源 LaunchAgent 对应的数据目录启用，不给其他部署或测试目录凭空增加告警。这能覆盖资源任务单独停摆；整机掉线或两个观察者同时停摆仍须外部监控。

## 磁盘口径与历史调查

早期调查把文件系统即时空闲误当 macOS 全部可用空间，导致用户仍有大量预计可回收空间时收到严重告警。现已改用 macOS Important Usage 估算可用空间，页面和通知另列即时空闲；读取失败报未知，不能退回旧口径断言严重。详见 [存储管理](server-storage-management.md)。当前门槛仍为估算口径使用率 80%／90%，或可用 5／2 GiB；inode 独立 80%／90%，并保留原恢复回差。

历史目录分配量仅用于解释当时即时空闲较少，不是当前容量结论，也不能相加作为精确归因。未删除缓存、开发工具、iCloud 文件或备份，未操作下载状态。此次告警范围收窄不改变已经修复的磁盘口径、数据保留或存储推送。
