## 1. 用户要求与目标

用户已优化并确认车辆参数，要求重新审视 Web、提出建议与设计方向，随后明确：“可以参考我已经手动确认的参数，以字典为准”。本轮进一步要求设计文件，将切换 GPT 模型执行。

目标是形成适合单车日常查看的桌面看板：进入页面即可理解最近车况、电量续航、充电与行程；详情能够追溯到字典和既有人工确认；后台采集的新数据能够自动进入页面。

成功条件：

1. 同一字段跨页面名称、单位、解释来源一致；已确认成果不会因普通数值变化失效。
2. 网页展示服务端已取得的最新快照，同时如实显示车辆数据时间；页面轮询不新增车辆云端请求。
3. 各车门和车窗独立展示，单项变化不抹掉其他位置的有效结果。
4. 总览首屏包含主要状态、电量续航和最近活动；记录摘要不依赖打开地图。
5. 参数字典默认用于查询，编辑、研究依据和原始数据按需展开。
6. 保留现有采集、通知、认证、历史数据和工作区中已有功能。

## 4. 字典、人工确认与展示规则

### 4.1 唯一术语来源

运行时权威文件为 `zeekr_control/parameter_dictionary.json`。`docs/vehicle-parameter-dictionary-2026-09-18.*` 是历史说明和快照资料，不作为当前数值来源。

按完整字段路径匹配字典，禁止仅按末级字段名匹配，以免动力电池和低压电池等重名字段混淆。所有页面名称、单位和说明由同一后端展示模型输出。中文别名可用于搜索，主标题仍用字典名称。

字典名称／单位与人工文本不同：以字典为准，在详情保留人工原文。不要静默覆盖字典、删除人工记录或因词典版本变动清空确认。

### 4.2 字段类型与确认范围

在字典定义中补充最小的结构化类型元数据，例如 `kind`：number、enum、boolean、text、timestamp。仅为明确类型的字段填写；不依据“原值能转成数字”推断类型。

| 字段类别 | 确认的内容 | 数值改变后的行为 |
|---|---|---|
| 连续数值，如电量、里程、胎温 | 字段含义与单位 | 保留字段说明确认，展示新读数 |
| 枚举，如通风档位、灯光状态 | 特定原值对应的解释 | 新码没有映射时显示未知／原值；原确认仍可查 |
| 布尔 | 字段含义，以及已明确的 true/false 语义 | 不从“已确认名称”推导另一取值的含义 |
| 特殊值，如剩余时间 2047 | 对这个值的有效性或疑问 | 保留专门状态，不显示为正常分钟数 |

首版采用兼容读取：既有核实记录保留不变。对明确的连续数值字段，可从已有 confirmed 记录派生“字段说明已确认”，无需把数据库 scope 批量改成 field。question、na 和具体值的争议不能被该兼容逻辑覆盖。

现有 `meaning` 是自由文本，可能只是“动力电池电量”“副驾通风状态”等字段名称；不能自动当成显示值，不能用中文关键词推导开／关。新增枚举映射仅使用现有可执行解码规则或明确结构化的值映射；没有映射时保留数据并显示相应说明，不重新要求用户核实全部参数。

多条记录互相冲突时，保留原文与“解释存在差异”，继续采用字典和已验证系统规则，不自动用最新字符串覆盖业务判断。人工输入 conversion 只作记录，不执行。

### 4.3 单项字段展示模型

保留现有接口字段，新增属性采用兼容方式。建议每个字段提供以下独立信息：

| 属性职责 | 内容 |
|---|---|
| 标识 | path、key、group |
| 字典信息 | name、unit、kind、reference |
| 读数 | raw、有效数值或 null、display_value |
| 有效性 | valid、missing、invalid、sentinel、unknown_enum |
| 解释依据 | 字典、已有系统解码、人工记录引用 |
| 确认状态 | 字段说明确认与当前值映射确认分别表示 |
| 适用性 | applicable、not_equipped、not_applicable、unknown |
| 时间 | 字段时间；无独立字段时间时明确使用整车时间 |

确认程度、车况好坏、数据时间和设备适用性是四个不同维度，不能互相代替。字段名称已确认不意味着“状态正常”；数据变旧也不取消字段确认。

### 4.4 本车配置

在现有车辆 profile 增加最小结构化配置映射，按车辆隔离；字典继续保存通用解释和车型参考。仅录入用户已明确确认的配置，来源标注车主确认。

未配备的设备退出日常车况卡，不按“关闭”计入正常项。参数字典仍可查该路径、原值和配置说明。缺少本车配置时显示适用性未知，不按零值推断未安装。

## 5. 共享最新快照与更新流程

### 5.1 方案选择

新增独立的私有最新快照存储，例如 `snapshots.sqlite3`，与轨迹和核实数据库位于同一应用数据目录。按账号／会话作用域与车辆摘要隔离，保留每辆车的最近有效快照；不建设长期全字段时序库。

选择独立存储是因为现有查询缓存会过期、轨迹库仅保存位置观测。不要直接延长 QueryPolicy 的查询缓存期限，以免破坏 60 秒请求保护语义。

建议独立 `snapshots.py` 负责读写，`web_model.py` 负责展示投影。避免前端或页面处理函数直接解析数据库中的完整原始响应。

### 5.2 内容与隔离

- 持久字段至少包括 schema_version、scope_key、vehicle_key、state_time、fetched_at、observed_at、raw 和生成车辆展示所需的元数据。
- scope_key 由服务端当前会话的稳定摘要产生；不向浏览器返回令牌、会话摘要或原始 VIN。相同会话重启可读，账号／会话变化后不能复用旧作用域。
- 保存私有文件的用户、目录权限、文件权限沿用现有 700/600 规则；读取不初始化监控或触发通知。
- `storage.load()` 当前只接受值全为字符串的字典，不能直接拿它读取嵌套快照；专用存储应有自己的结构校验。
- 浏览器只收到公开展示投影。完整原始响应、车辆身份、精确坐标和地址不加入普通 `/api/state` 或新事件摘要。

### 5.3 写入与时间规则

后台 `Runner.tick()` 与手动 `App.refresh()` 成功取得合法状态后都可以提交快照，使用同一事务化写入口：

1. 先校验当前会话作用域和车辆归属，再处理快照；失败请求不写新车况。
2. state_time 严格更新时替换当前快照；时间倒退不覆盖较新的有效快照。
3. 时间相同时允许有效内容发生修正，但保留相同车辆时间，不宣称车辆产生了新数据；页面修订标识可反映内容变化。
4. 没有合法车辆时间的响应不能替换已有带有效时间的快照；首次只有无时间数据时可以显示，但标明更新时间未知。
5. observed_at 是程序处理时间，fetched_at 使用实际云端读取时间；命中查询缓存时不能伪装成刚从车辆获得数据。
6. 并发写按车辆／作用域事务比较时间，旧请求迟到不覆盖新快照。写失败保留旧快照，产生可见且不含敏感内容的错误状态。

### 5.4 读取与初始化

- `/api/state` 只读本地存储和服务状态，不创建 Client 查询云端。
- 首次进入：当前有效会话有匹配快照时直接显示并标明时间；没有时保持明确空态，可手动刷新，也可等待现有后台采集。
- 页面轮询继续使用现有约 5 秒节奏；后台新快照在下一次成功轮询中反映。隐藏页面暂停轮询，恢复后同步。
- 手动刷新保留现有 60 秒账号间隔、跨进程锁、429 冷却和失败保留旧值行为。按钮名称继续使用“刷新状态”，避免与旧自动化和用户习惯冲突。
- 当前选择车辆与后台绑定车辆分开；浏览另一辆车不改变采集绑定。切换账号／车辆时清空不匹配的内存展示和历史选择，不允许迟到响应串车。
- 采集暂停或后台离线时仍显示已保存快照，并明确其时间；不能显示为正在获取新车况。

## 6. 各页面设计与行为

### 6.1 总览

- 顶部把“服务已连接”“车辆账号状态”“车辆数据更新时间”分开。主提示为车辆数据时间，不能用心跳时间替代。
- SOC 与剩余续航为主要数字；累计里程退到辅助行。单位来自字典，未知不填零。
- 门窗摘要显示可理解的事实，并能跳到车辆页对应区域；没有已验证开门枚举时，不能仅为完整视觉效果生成“打开”。
- 活动卡使用已有监控活动与车辆解释：充电、行程记录中、等待行程结束确认、没有活动证据。历史快照标注“最近观测”，不宣称实时驾驶状态。
- 没有充电或行程证据不等于停车已确认；车速无效或 0 不能单独证明停车。
- 展示最近一段已结束行程和最近一次已结束充电。优先当前车辆；如最近记录是部分记录，直接标注，不用更早完整记录伪装“最近”。
- 低温／胎压阈值和停车未锁提醒不新增推断规则；展示已有明确事实即可。

### 6.2 车辆

- 每个车门／窗先按本位置原值生成结果；现有能解释的 0 值保持关闭，未识别值仅使本位置未知。
- 现有锁止规则依赖组合时，继续保留组合要求；不要为了逐项 UI 擅自扩展单个锁码的语义。
- 四门四窗再汇总：全部关闭需四项有效且关闭；有已验证打开项时列具体位置；其余给出“已知关闭 N 项，M 项未知”。
- 尾门、中控锁、前舱盖独立处理，前舱盖没有规则时保留未知。
- 上方为紧凑门窗图示与文字，下方两列为轮胎和座舱；保养与低压电池为第二层。
- 胎压详情保留当前精度，总览维持一位小数；温度使用温度自己的时间。保养和低压指标来自字典，不能把辅助电池 SOH 称为动力电池健康。
- 待核实设备不铺满日常页；已确认本车不适用的设备仅留参数入口。

### 6.3 能源与充电

布局保持稳定：左上为电量续航，右上为当前能源活动；下方为最近行程和最近充电摘要；依据与原值在末尾折叠。

| 场景 | 当前能源活动卡 |
|---|---|
| 充电中且证据充分 | 充电模式、SOC、有效剩余时间、已知会话起点和当前变化 |
| 已停止 | “充电已停止”，显示最近会话摘要；不擅自写“已拔枪”或“已充满” |
| 未充电 | 车辆上报平均电耗及最近行程入口；充电参数降为详情 |
| 不确定／矛盾 | “充电状态未知”，保留有效电量和续航，详情可查依据 |
| 缺失数据 | 简短空态，避免大面积不可计算指标 |

- 车辆上报平均电耗与本次行程估算电耗分别展示；统计窗口不明时用固定脚注说明。
- 估算耗电量 = 该事件保存的电池容量 ×（起点 SOC − 终点 SOC）÷ 100。
- 估算行程电耗 = 估算耗电量 ÷ 实际里程 × 100；只用于完整、同一行程、距离大于 0、SOC 有效且消耗大于 0 的记录。
- 估算充入电量 = 该事件保存的电池容量 ×（终点 SOC − 起点 SOC）÷ 100；部分记录仅展示已观测 SOC 变化，不作为完整充电量。
- 历史事件没有容量或关键数据时不拿当前车辆资料补算历史值；显示无法估算的具体原因。
- 达成率继续沿用 `energy.read_attainment()` 已有口径，作为次级详情。不要改成剩余续航除以标称续航。
- 字典名称和已确认读数可以直接展示；新增功率计算、充电费用和累计效率本轮不做，避免引入额外电气测量口径。
- 2047 等无效时间码不画倒计时，question 记录仍可查。

### 6.4 行程与轨迹

- 保留“本地记录／云端历史”来源区分。本地默认显示行程摘要列表，采样时间线和路线为详情。
- 按北京时间日期筛选，上一天／下一天／今天操作保持选中来源；支持无记录、读取失败、部分记录三种不同状态。
- 新摘要列表复用 `monitor_events`，筛选当前车辆且默认只列 trip_end；能源页读取 charge_end。charge_start 只作活动事件，不重复计为一次完成充电。
- 每条至少包含开始／结束时间、观测时长、里程（行程）、起止 SOC、变化及完整性。地址、坐标和路线不属于默认摘要。
- 完成事件的日期以结束时间落入所选北京时间日期为准；跨午夜保留原起止时间。创建通知时间不替代事件发生时间。
- 每页 20 条，按结束时间与稳定 ID 倒序，分页保持稳定；总览只需要最近条目，不加载全历史。
- 选择本地行程后，按同车、起止时间范围筛选本地观测作为候选路线，沿用现有可信度与分段规则；无路线可用也保留摘要。
- 路线仍由用户主动显示；切换日期或行程清空旧路线，迟到响应不覆盖新选择。
- 云端历史保持本地当前能力；线上未接通仍如实显示连接状态，不为本轮布局工作自动发起真实查询。

### 6.5 参数字典

默认浏览：顶部一行搜索和分类，下面为“名称、当前值、单位、适用性／解释状态”的清单。原始路径、原值、字典依据和人工记录在选中项详情；桌面可沿用主从两栏，减少顶部进度区占高。

- 默认展示本次有有效返回的非敏感字段，沿用现有未知项隐藏规则。日常关键指标即使缺失仍在其卡片明确表示无数据。
- 搜索覆盖字典名称、完整路径、单位、说明与人工别名；结果主名称按字典。
- 保留分类、已确认、有疑问、不适用等筛选。连续数值的字段确认与枚举当前值映射状态分开显示。
- “编辑核实”进入既有编辑流程；进度统计和“保存并下一项”只在该模式占主要位置。
- 保存、清除、撤销、版本冲突检测、失败保留、样本时间与草稿保留继续有效。后台新快照不得替换正在编辑的原始样本。
- 用户正常浏览不需要填写或确认任何字段。自由文本记录不自动参与通知或车辆业务判断。

### 6.6 定位与设置

- 定位保持现有主动显示、独立坐标开关、可信标记、分段与底图边界；更新车况不重建用户正在操作的地图。
- 设置将采集状态与通知状态放在同一区域，暂停含义保持现状：暂停自动检查、采样与通知处理；服务重启默认恢复。
- 存储文案统一为“数据保存在运行服务的设备上”；部署信息明确时补充“服务器”或“本机开发环境”。回环监听不等于没有反向代理访问，不据监听地址写“仅本机访问”。
- 会话已保存、最近读取成功、会话失效分别表示；浏览器连接成功不代表车辆数据实时。
- 不新增短信登录、密码修改、数据删除、自动恢复旧备份入口。

## 7. API、模块与状态保持

### 7.1 接口方向

| 接口 | 设计 |
|---|---|
| GET /api/state | 保留现有响应，增加快照修订信息、统一字段解释、当前车非位置摘要；纯本地读取 |
| POST /api/refresh | 保留当前校验与限流，成功后写共享快照，再返回统一状态 |
| GET /api/events | 新增本地事件摘要查询；参数为已授权车辆选择、北京时间日期、kind、cursor；无外部请求 |
| GET /api/tracks | 保留原日期查询；需要行程范围时新增受校验的开始／结束范围，车辆选择必须合法 |
| POST /api/field-reviews | 保留现有写入、revision 冲突与撤销语义；兼容派生展示不写回旧记录 |
| /api/history 系列 | 保留当前分支既有实现及用户主动查询规则 |

新接口沿用 Web 登录、同源、身份和车辆选择规则。事件摘要使用显式字段白名单；不要把 `monitor_events.message` 或包含 start_location、end_location、地址的完整 summary 直接发给默认页面。

当前 `monitor_runtime.read_status()` 查询最近事件没有按车辆过滤，不能直接拿其 events 作为新页面的车辆摘要。应新增专门的只读事件查询，并校验事件 ID 属于当前选择车辆。

### 7.2 建议模块边界

| 现有／建议文件 | 职责 |
|---|---|
| parameter_dictionary.json / parameter_dictionary.py | 字典与结构化字段类型，统一术语入口 |
| field_reviews.py / static/field-reviews.js | 保存语义保持、确认展示兼容、浏览和编辑模式 |
| profiles.py | 本车结构化配置及展示资料 |
| web_model.py | 统一字段展示、逐项门窗解释、时间和适用性 |
| snapshots.py（新增） | 最新快照的作用域、事务写入、恢复与只读读取 |
| events.py（新增） | 按车／日期的只读事件摘要与分页，输出非位置白名单 |
| monitor_runtime.py | 成功读取后发布共享快照，不更改事件检测与采样策略 |
| web.py | 统一状态响应、选择车辆、接口接线与错误语义 |
| static/app.js / app.css / index.html | 页面层级、增量更新、稳定交互与导航 |
| energy.py / vehicle_state.py | 尽量复用既有有效规则；仅因本轮必要且有证据的修正才改动 |

新增模块名称可按仓库习惯调整，但职责应保持分离。不要求把所有前端重构成框架或重新组织整个项目。

### 7.3 页面更新

- 快照内容修订、人工记录 revision、车辆选择、后台活动、最近事件分别触发相关区域更新。
- 地图实例、缩放、中心、时间滑块、日期、列表选中项、展开项、滚动、焦点和编辑草稿都应在无关轮询后保留。
- 如果暂时保留整块 HTML 重绘，应明确保存／恢复上述状态；地图区域优先独立，不在每次 render 时 remove。
- 同一请求失败保留数据与原时间；恢复连接后移除错误。通知、保存等状态用现有 aria-live／role=status 机制表达，不抢焦点。
