# Web 复审与设计方向

日期：2026-09-18。状态：审查与设计建议，尚未实施。

本轮以用户已确认的车辆参数为前提，以 `zeekr_control/parameter_dictionary.json` 为名称、单位与说明的统一来源，参考已保存的人工核实记录。目的在于改善日常使用，不重复开展整套车辆参数核实。

## 审查依据与边界

- 只读核对线上 `current`：`/opt/zeekr-control/releases/20260918-parameter-dictionary`；Web 与监控服务均为 active。
- 只读核对线上核实数据库：71 条记录、71 个字段路径；70 条已确认、1 条有疑问；全部以 `value` 范围保存。
- 线上与本地的 `web_model.py`、`vehicle_state.py`、`field_reviews.py`、`static/field-reviews.js` 内容相同；主页面资源及历史功能有差异。线上云端历史仍显示尚未接入。
- 使用线上代码副本、临时数据库和合成车辆，在 Chromium 中查看总览、车辆、能源、参数、轨迹、设置页面；视口为 1440×900，并补查 1280×800 参数页。车型显示资料显式设为测试用资料，截图不代表当前实车读数或线上登录页面。
- 复现单门／单窗变化导致全部门／窗变为未知，以及数值变化后人工核实退回部分确认；页面检查无 JavaScript 错误。
- 本地展示模型 14 项、词典 5 项测试通过；参数过滤与核实规则脚本通过。这些检查不能替代新设计验收。
- 本轮没有调用真实车辆刷新、控制或云端历史接口，没有更改线上数据、服务或程序代码。

## 主要发现

| 优先级 | 发现与证据 | 使用影响 | 设计建议 |
|---|---|---|---|
| 高 | `web.py` 的主展示模型在手动 `refresh()` 时生成，`state()` 返回内存中的原模型；后台采集状态另行读取 | “采集正在运行”容易被理解成主车况也自动更新，实际两者可能不同步 | 主页面读取后台已保存的最新车辆快照；进入页面和页面轮询不额外查询车辆云端。保留手动刷新及限流提示 |
| 高 | 核实记录均按具体原值保存，包括 SOC、温度、里程等连续数值；`reviewStatus()` 在原值改变时返回 partial | 确认过的字段随读数变化再次成为部分确认 | 数值字段的名称／单位确认与具体读数分离；枚举解释仍匹配具体原值。保留现有记录，不把自由文本直接当成开关或档位映射 |
| 高 | `build_model()` 先计算四门／四窗整体布尔值，再复制到每个位置 | 单个车门或车窗变化会抹掉其他位置已知状态 | 各位置分别解释，再汇总整车。单项未知仅影响该项；聚合“全部关闭”仍需要所有相关部位的有效证据 |
| 高 | 字典和人工记录用于参数页面；主页面依赖独立硬编码文案及规则 | 同一个字段在不同页面出现不同名字、单位或确认状态 | 所有页面从同一展示模型取名称、单位、值、状态、时间和来源。字典优先，人工确认补充本车上下文；算法和通知规则保持可追溯 |
| 中 | 线上已经存在行程和充电事件，页面主要在设置中列出通知类型与发送状态 | 有价值的行程、充电记录难以浏览 | 建立事件摘要列表：行程与充电可分别过滤，清楚标记完整／部分记录。近期事件无需打开位置即可查看 |
| 中 | 合成场景下，1440×900 总览行程标题在约 1022 px；参数清单标题在约 528 px | 首屏优先展示车图、说明和核实进度，日常信息靠后 | 压缩车图和顶部重复说明，把当前状态与最近活动放进首屏；参数页默认查询和浏览 |
| 中 | 设置与页脚仍有“本机保存”“仅本机访问”等固定文案，而实际服务运行在服务器 | 用户可能误解数据存储位置和访问边界 | 用部署信息生成文案：本次部署显示“服务端保存”；服务连接、账号会话、车辆数据时间分别呈现 |
| 中 | 主内容通过整体替换重绘，重绘前会移除地图 | 状态更新可能打断地图缩放、回看与阅读位置 | 更新变化的内容，保留地图、日期、选中记录、展开项、滚动和焦点 |

对上一轮结论的修正：当前后端锁车标签只输出“已锁车”或“未知”，没有已验证的“未锁车被着成绿色”路径。颜色应按状态含义设计，但该项不能列为已复现现象。

## 推荐方向

采用“日常总览 + 专题详情 + 参数资料”的组织方式，保留现有浅色、青绿色风格及主要技术结构。先统一数据表达，再调整页面。

可选择的方案：

1. **日常看板，推荐。** 首屏回答车况、电量、充电、最近行程四个问题；参数和详细依据按需查看。最适合当前单车、桌面使用。
2. **参数工作台。** 保留高密度字段列表和核实编辑作为主入口，适合持续协议研究，但日常看车需要更多筛选。
3. **统计分析中心。** 首页以周／月趋势和对比为主，需要更多连续、完整、口径统一的历史数据。当前优先级低于前两者。

## 信息架构与页面职责

建议侧栏分成两组：常用为“总览、车辆、能源与充电、行程与地图”；资料与管理为“参数字典、设置”。首次实施可以先保留既有页面入口，在内部完成内容调整，再合并地图与轨迹导航。

| 页面 | 默认展示 | 次级内容 |
|---|---|---|
| 总览 | 车辆数据时间、明确的当前状态、SOC、剩余续航、当前活动、最近完成事件、简洁胎压／温度 | 车图、累计里程、完整时间、字段解释 |
| 车辆 | 四门四窗逐项状态，尾门／前舱盖，轮胎与座舱 | 本车已配备的舒适功能、保养指标、低压电池；原始字段链接 |
| 能源与充电 | 当前电量与续航；充电时显示当前会话，平时显示近期能耗与充电摘要 | 续航达成率、桩侧电压／电流、计算依据、原值 |
| 行程与地图 | 最近行程列表、时间／时长／里程／SOC 变化、记录完整性 | 用户主动展开路线、当前位置、本地采样时间线；云端历史连接状态 |
| 参数字典 | 搜索、分类、中文名称、当前值、单位、本车适用性 | 原始路径、原值、来源、人工记录；点击后进入编辑 |
| 设置 | 后台采集与通知状态、暂停／继续、账号状态、服务端存储与位置显示 | 数据库大小、采样策略、接口与部署细节 |

### 总览布局

建议 1440×900 首屏按以下顺序组织：

| 区域 | 左侧 | 右侧 |
|---|---|---|
| 顶部状态条 | 车型、车辆数据更新时间、缓存说明 | 读取最新缓存、服务状态 |
| 主要区域 | 电量、剩余续航、门窗锁车摘要 | 当前活动卡：充电／行程记录／停车摘要 |
| 次要区域 | 胎压与温度简表 | 最近一段行程或最近一次充电 |

车图作为辅助视觉，可缩小放在车型区。维持卡片位置，随场景更新活动卡内容，避免每次充电或停车后整页跳位。

### 车辆页

- 单项先解释，整车后汇总。已知关闭的三扇车门不因另一扇门未知而失去结果。
- 普通状态直接写“左前车门打开”等事实；满足足够场景条件后才形成“停车后仍未锁”等提醒。
- 不把“状态未知”计为故障；确认未配备的设备退出日常状态区，仍可在参数字典追溯。
- 胎压与胎温、车内外温度、保养剩余天数／里程、低压电池各有固定区域。有效但不常用的指标放在详情，缺失不填零。

### 能源页

- 充电中：状态、SOC、有效剩余时间、当前会话变化优先；电压电流沿用字典命名。充电功率仅在同侧电气量、单位和时间条件满足后计算。
- 未充电：展示最近完整行程的里程、时长、SOC 变化与估算耗电，以及最近充电摘要。
- “车辆上报平均电耗”与“本次行程估算电耗”分别标注。字典确认了名称和单位，并不自动证明平均电耗的统计窗口等于最近一次行程。
- 续航达成率保留为次级指标。短途及很小 SOC 差值不适合作为首页大数字；无可算行程时使用简短空态。
- SOC 换算电量称“估算耗电／估算充入电量”，不作为充电桩结算电量。历史中早期可疑或部分事件不直接混入累计统计。

### 参数字典页

- 用户已确认的成果成为日常展示依据；默认浏览模式，编辑是主动进入的操作。
- 主表列为“参数、当前值、单位、分类”；原始路径和研究说明放在详情。
- 不再让全部参数默认呈现为一张待完成的核实任务表；进度统计移到编辑模式。
- 保留已确认／有疑问／不适用筛选，以及核实记录和撤销能力。
- 字典名称与人工文本冲突时，页面以字典为准，并在详情保留原记录；不丢弃用户输入、不静默改写枚举语义。
- 数值型字段建立独立的字段说明确认；状态型字段保持按值映射。整理既有记录时按字段类型处理，不因原值恰好是数字就把它当连续量。

## 数据表达约定

每一项展示信息分别保留：字段完整路径、字典名称、字典单位、实际读数、解释后的状态、适用性、确认依据、车辆／字段时间。以下维度互不替代：

- **含义与单位**：依据字典及已有人工确认。
- **值与状态**：依据当前接口值和已确认映射；未知枚举仍保留原值。
- **适用性**：已配备、未配备、不适用、尚不明确。
- **时间**：服务可连接、最近采集成功、车辆数据更新是三个不同事实。

后台已有更新时，Web 获取服务端保存的快照即可更新主车况。后台采集继续沿用现有频率与限流；手动刷新和云端历史查询保留各自的用户入口，页面轮询不额外发起车辆云端查询。服务重启后可展示最近保存快照，并标明它的原始时间。

视觉状态保持克制：正常或中性信息以深色文字呈现；需用户处理的事件使用强调色；未知使用灰色文字加明确标签；不能只靠颜色表达含义。刷新、保存、连接恢复使用简短状态信息，避免刷新焦点或重复打断阅读。

## 建议实施顺序与验收

1. **数据一致性。** 字典贯通、确认范围整理、逐门逐窗独立解释、后台快照与页面同步、部署文案纠正。验收：数值变化不会丢失字段确认；未知枚举不被扩大解释；后台新快照进入页面不新增车辆云端请求；旧时间不因网页刷新变新。
2. **日常页面。** 总览压缩车图，能源按当前活动突出信息，车辆详情按本车配置整理。验收：1440×900 与 1280×800 均可快速找到状态、电量、充电和最近事件；必要信息不依赖展开原始参数。
3. **记录浏览。** 复用已保存的行程／充电事件建立摘要入口，再连接地图与参数详情。验收：隐藏位置时仍能看非位置摘要；部分记录清楚标注；云端未连接不被表现成没有行程；新状态到达不重置地图和选中记录。

## 设计参考

- [NN/g：Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)：常用信息在第一层，低频详情按需展开。用于参数详情和依据说明的层次划分，不直接推导本车具体布局。
- [W3C：Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)：状态同时用文字或形状表达，颜色作为辅助。
- [W3C：Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)：刷新、保存、连接等状态变化应能被辅助技术识别。
